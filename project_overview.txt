1. PROJECT IDENTITY & ABSTRACT
================================================================================
Project Title   : Campus Trace - Real-Time Geolocation & Student Tracking System
Abbreviation    : STMS (Student Tracking and Monitoring System)
Target Domain   : Smart Campus Telemetry, Web-GIS, Institutional Safety & Auditing
Application Type: Single Page Application (SPA) with Persistent Full-Duplex WebSockets
Core Philosophy : 100% Zero-Dedicated-Hardware, Browser-Native, Privacy-Enforced

Abstract:
Campus Trace is an event-driven, fullstack geospatial platform designed to track 
student presence and location across educational campuses in real time during 
mandated college operating hours (9:00 AM to 4:15 PM IST). By eliminating the need 
for proprietary hardware (such as RFID scanners, BLE beacons, GPS tags, or wearable 
bands) and removing app-store distribution friction, students connect directly 
via their smartphone's mobile browser (iOS Safari, Android Chrome). Utilizing the 
HTML5 Geolocation API and a persistent bi-directional Socket.IO communication pipe, 
telemetry coordinates are streamed to an administrative GIS command console built 
with React 19, Leaflet.js, and OpenStreetMap. The system features in-place memory 
deduplication, a strict 80-student concurrency guard, automatic viewport 
re-bounding, and a 24-hour sliding-window disconnect retention mechanism.

2. PROBLEM STATEMENT & INSTITUTIONAL MOTIVATION
================================================================================
Academic institutions face acute challenges in ensuring student accountability, 
monitoring campus boundaries, and locating individuals during medical or campus 
emergencies:

A. Critical Limitations in Legacy Systems:
1. Static RFID / Smart Card Turnstiles:
   - Only log isolated, discrete timestamps at entry/exit gates.
   - Zero spatial awareness once students cross checkpoints (cannot detect bunking, 
     campus perimeter breaches, or medical distress).
2. Bluetooth Low Energy (BLE) Beacons:
   - Restricted to micro-zones (< 30 meters range).
   - High hardware procurement, battery replacement, and beacon density costs.
   - Suffer from signal reflection and indoor multipath fading.
3. Biometric Scanners (Fingerprint / Facial Recognition):
   - Fixed physically to walls; causes bottleneck queues during peak arrival times.
   - Strictly records attendance; provides zero continuous tracking.
4. Dedicated GPS Hardware Trackers / Wearable Bands:
   - Prohibitive capital expenditure ($30–$100 per device across thousands of students).
   - High rate of physical damage, loss, charging failures, and logistical overhead.
5. Native Mobile Apps (App Store / Google Play):
   - Friction of app downloads, mandatory updates, and permission resistance.
   - Modern mobile OSs (iOS/Android) aggressively terminate background native services.
   - Triggers student resistance regarding 24/7 covert surveillance.
6. Traditional HTTP Long-Polling Web Applications:
   - High latency (1,500 ms – 3,000 ms).
   - Massive network overhead: every coordinate push sends ~800 bytes of redundant 
     HTTP headers and requires repeated TCP 3-way handshakes.
   - Severely drains mobile battery and cellular data plans.

B. Campus Trace Proposed Solution:
An ultra-lightweight, browser-native Web-GIS platform combining:
- Zero Hardware Overhead: Runs instantly on any smartphone with a web browser.
- Sub-60ms Streaming Latency: Single persistent WebSocket channel with ~6-byte frame overhead.
- Strict Privacy Time-Boxing: Automated hard cut-off outside official college hours.
- State Deduplication & 24h Fail-Safe: Single-row persistence per student with last-known 
  disconnect coordinate freezing for 24 hours.

4.1 backend/server.js (Application Gateway & Socket Engine)
--------------------------------------------------------------------------------
Key Responsibilities:
- Initializes HTTP server and binds the Socket.IO WebSocket server with CORS policy.
- Serves static production assets from frontend/dist for single-port deployment.
- Hosts REST endpoints: GET /api/history and GET /api/history/stats.
- Manages Socket.IO connection lifecycle, room subscriptions, and event routing.

Core Functions & Mechanics:
1. isCollegeTime():
   - Uses new Date().toLocaleString("en-US", { timeZone: "Asia/Kolkata" }).
   - Calculates current IST hours and minutes.
   - Evaluates:
       if (hours > 9 && hours < 16) return true;
       if (hours === 9 && minutes >= 0) return true;
       if (hours === 16 && minutes <= 15) return true;
       return false;
   - Purpose: Prevents spoofed client system clocks by enforcing server-side time 
     calculated in the Indian Standard Time (IST) zone.

2. socket.on('joinAdmin'):
   - Subscribes the admin's socket connection to an isolated room named 'admin'.
   - Immediately emits 'initialStudents' containing the current activeStudents map, 
     enabling instant map hydration without waiting for fresh transmissions.

3. socket.on('updateLocation', data):
   - Accepts payload: { id, name, semester, lat, lng, bypass }.
   - Step 1 (Time check): If bypass is false and isCollegeTime() is false, emits 
     'trackingError' ("Outside of college hours") and halts processing.
   - Step 2 (Capacity check): Checks if Object.keys(activeStudents).length >= 80. 
     If full and socket.id is not already an existing active student, emits 
     'trackingError' ("Campus tracking capacity full (Max 80 students)") and aborts.
   - Step 3 (Normalization): Trims strings and falls back to default labels 
     ("Student-XXXX", "Unspecified").
   - Step 4 (RAM Update): Stores entry in activeStudents[socket.id] with coordinates, 
     metadata, and timestamp.
   - Step 5 (History Persistence): Calls historyStore.updateOrAddStudentLocation().
   - Step 6 (Broadcast): Emits 'studentLocationUpdate' and 'historyUpdated' to 'admin'.

4. socket.on('disconnect') & socket.on('stopTracking'):
   - Cleans up activeStudents[socket.id].
   - Emits 'studentDisconnected' to all clients in the 'admin' room.
   - Invokes historyStore.markStudentDisconnected(socket.id), freezing their final 
     coordinates and transitioning status to 'disconnected'.

4.2 backend/historyStore.js (In-Memory Deduplication & 24h Retention Engine)
--------------------------------------------------------------------------------
Key Responsibilities:
- Maintains an in-memory cache (historyCache) for O(1) state mutations.
- Persists all changes to a flat JSON file (backend/data/location_history.json).
- Implements single-row deduplication per student.
- Enforces an automated 24-hour sliding retention window.

Core Functions & Mechanics:
1. initStore():
   - Verifies the existence of backend/data/; creates directory recursively if absent.
   - Reads location_history.json, parses JSON array, loads into historyCache, and 
     runs an initial cleanup cycle.

2. getStudentKey(name, semester):
   - Computes: `${name.trim().toLowerCase()}___${semester.trim().toLowerCase()}`
   - Guarantees that whether a student updates coordinates 1 time or 10,000 times, 
     they map to exactly one record in the storage system.

3. updateOrAddStudentLocation({ name, semester, lat, lng, socketId }):
   - Generates composite key.
   - Searches historyCache using findIndex(item => item.studentKey === key).
   - If Student Exists:
     Updates lat, lng, socketId, sets status = 'connected', clears disconnectedAt, 
     and refreshes timestamp = current ISO time. Moves record to the front of 
     historyCache (unshift) to maintain reverse chronological order.
   - If New Student:
     Constructs unique record object:
     {
       id: `student_${Date.now()}_${Math.random().toString(36).substring(2,6)}`,
       studentKey: key,
       name, semester,
       lat: Number(lat), lng: Number(lng),
       socketId, status: 'connected',
       firstConnectedAt: nowISO,
       disconnectedAt: null,
       timestamp: nowISO
     }
     Pushes to top of cache and executes persistToDisk().

4. markStudentDisconnected(socketId):
   - Iterates through historyCache.
   - Locates matching socketId with status === 'connected'.
   - Sets status = 'disconnected', disconnectedAt = nowISO, and resets timestamp = nowISO.
   - Resetting timestamp ensures the 24-hour retention countdown starts at the exact 
     moment of disconnection.

5. cleanupOldRecords():
   - Cutoff calculation: Date.now() - (24 * 60 * 60 * 1000).
   - Filters historyCache: keeps items where new Date(item.timestamp).getTime() > cutoff.
   - If records are pruned, triggers persistToDisk().
   - Scheduled to execute automatically every 15 minutes via setInterval.

6. getHistory({ search, semester }) & getStats():
   - Performs case-insensitive substring searching across name and semester.
   - Filters by selected semester category.
   - Computes aggregated stats: totalStudents, activeNow, disconnected, unique semesters.

4.3 frontend/src/pages/StudentTracker.jsx (Mobile Edge Telemetry Client)
--------------------------------------------------------------------------------
Key Responsibilities:
- Provides a clean, responsive mobile interface for students to initiate location streaming.
- Interfaces with the browser's HTML5 Geolocation API.
- Manages WebSocket lifecycle and handles transmission errors.

Core State & Mechanisms:
1. Local Storage Integration:
   - Reads studentName and studentSemester from localStorage on mount.
   - Caches inputs automatically on submission so students do not need to re-enter 
     credentials upon subsequent visits.
2. Geolocation Watch Stream:
   - Invokes navigator.geolocation.watchPosition(successCallback, errorCallback, options).
   - Options configured: { enableHighAccuracy: true, maximumAge: 0, timeout: 10000 }.
   - successCallback extracts coords.latitude and coords.longitude, updates position state, 
     and emits 'updateLocation' over the socket.
3. Operating Hour Guard & Bypass:
   - Includes client-side isCollegeTime() mirror check for instant UI feedback.
   - Developer Bypass Checkbox: Allows authorized testing outside 9:00 AM - 4:15 PM IST.
4. Error Handling:
   - Listens to socket 'trackingError' event. Displays friendly alerts if college 
     hours are violated or campus capacity (80) is full.
   - Gracefully tears down watchPosition and resets tracking state on failure.

5.2 WebSocket Event Contract
--------------------------------------------------------------------------------
Client-to-Server Events:
- joinAdmin: Sent by admin dashboard upon connection to enter the 'admin' broadcast room.
- updateLocation: Sent by student tracker.
  Payload: { id: string, name: string, semester: string, lat: number, lng: number, bypass: boolean }
- stopTracking: Sent when student manually taps "Stop Tracking".
- disconnect: Native Socket.IO event triggered when network drops or tab closes.

Server-to-Client Events:
- initialStudents: Dispatched to admin upon joinAdmin. Contains active students map.
- studentLocationUpdate: Multicast to 'admin' room on valid telemetry packet.
- studentDisconnected: Dispatched to 'admin' room with socket.id of disconnected client.
- historyUpdated: Broadcasts full history record to admin to keep table synchronized.
- trackingError: Unicast to student client if out-of-hours or capacity exceeded.

6. NETWORKING, SECURITY & MOBILE ENVIRONMENT PROTOCOLS
================================================================================
A. Mandatory HTTPS Requirement:
Modern mobile operating systems (Apple iOS Safari, Google Android Chrome) enforce 
strict security policies: the W3C Geolocation API is completely disabled on 
insecure HTTP origins. To enable local Wi-Fi testing without purchasing commercial 
SSL certificates, the project integrates @vitejs/plugin-basic-ssl in frontend/vite.config.js. 
This dynamically generates a self-signed TLS/SSL certificate, exposing the Vite dev 
server over https://.

B. Remote Network Exposure (npm run tunnel):
When tracking devices operating on separate cellular networks (4G/LTE/5G) outside 
the local campus Wi-Fi network, the project includes an automated tunneling script:
  npm run tunnel -> ssh -R 80:localhost:5173 localhost.run
This establishes an encrypted reverse SSH tunnel, outputting a secure public HTTPS 
URL (e.g., https://xxxx.lhr.life) accessible from anywhere in the world.

7. MATHEMATICAL, ALGORITHMIC & THEORETICAL FOUNDATIONS
================================================================================
1. Geodetic Coordinate Representation (WGS-84):
Coordinates are acquired according to the World Geodetic System 1984 (EPSG:4326) 
standard as ellipsoidal latitude (phi) and longitude (lambda). Leaflet projects these 
coordinates onto a 2D plane using the Spherical Mercator projection (EPSG:3857):
  x = R * lambda
  y = R * ln(tan(pi/4 + phi/2))

2. Haversine Great-Circle Distance Metric:
To calculate physical ground displacement and verify geofence boundaries on a sphere:
  d = 2R * arcsin(sqrt(sin^2(delta_phi / 2) + cos(phi_1) * cos(phi_2) * sin^2(delta_lambda / 2)))
Where:
  R = 6371 km (mean radius of Earth)
  delta_phi = phi_2 - phi_1 (difference in latitude in radians)
  delta_lambda = lambda_2 - lambda_1 (difference in longitude in radians)

3. Transport Layer Protocol Efficiency (WebSockets vs. HTTP):
- HTTP Request/Response Model:
  * Requires a 3-way TCP handshake (SYN, SYN-ACK, ACK) and TLS negotiation per cycle.
  * Every transmission contains ~800 bytes of headers (User-Agent, Cookies, Accept).
  * Bandwidth for N updates: Overhead = N * 800 bytes.
- WebSocket Bi-Directional Streaming:
  * Single HTTP 101 Switching Protocols upgrade handshake over TCP.
  * Framed binary/text packets carry only a 2 to 6 byte header overhead.
  * Frame Overhead Ratio:
      Ratio = 800 bytes (HTTP) / 6 bytes (WS Frame) approx 133x bandwidth efficiency.

8. COMPREHENSIVE LITERATURE SURVEY & COMPARATIVE MATRIX
================================================================================
Academic Context & Prior Works Analyzed:
- Das et al. [1]: Integrated GPS, RFID, GSM, and GPRS for school bus & student tracking.
  Limitation: Costly dedicated hardware and ongoing cellular SIM charges per bus/tag.
- Kadam et al. [2]: RFID and Arduino Mega 2560 for automated classroom attendance.
  Limitation: Static gate scanning; zero continuous spatial tracking inside campus.
- Joseph & Moses [3]: Fingerprint authentication, ESP32, and Wi-Fi for attendance.
  Limitation: Point-in-time check-in; no real-time geographic awareness.
- Rayan et al. [4]: Android, Firebase, and SMS for attendance verification.
  Limitation: Tied to native Android ecosystem; lacks real-time administrative GIS mapping.
- Karkare et al. [5]: Android & GPS emergency live tracking.
  Limitation: Lacks institutional time boundaries and centralized multi-student management.
- Gandhi et al. [6]: BLE beacons, Arduino Nano, and mobile application for perimeter alerts.
  Limitation: Extremely limited coverage (< 30m) requiring dense beacon grid deployments.
- Meuleman et al. [11]: Online student portals and parental tracking.
  Limitation: Raised serious academic concerns over student privacy and autonomy loss.
- Gaikwad et al. [13]: Study Sync Wi-Fi and GPS campus presence validation.
  Limitation: Limited to schedule matching without live continuous coordinate vectors.
- Muthulakshmi et al. [14]: Wearable bands with RF, GSM, GPS, RFID, and fingerprint sensors.
  Limitation: Wearable hardware distribution is logistically prohibitive and prone to loss.

10. DEPLOYMENT, ENVIRONMENT SETUP & VERIFICATION GUIDE
================================================================================
Prerequisites: Node.js (v18 or higher) and npm installed.

Step 1: Start Backend WebSocket Server
  cd backend
  npm install
  node server.js
  -> Confirmed by terminal log: "Student Tracking Server is running on port 5000"

Step 2: Start Frontend Application
  cd frontend
  npm install
  npm run dev -- --host
  -> Runs Vite over HTTPS: https://localhost:5173

Step 3: Access Admin Command Console
  1. Open desktop browser and navigate to: https://localhost:5173/admin
  2. Accept self-signed SSL warning (Advanced -> Proceed to localhost).
  3. Login with credentials: ID = admin | Password = admin123.

Step 4: Connect Mobile Student Tracker
  1. Find host PC network IP from Vite terminal (e.g., 10.247.60.51).
  2. On mobile phone (connected to same Wi-Fi), open Chrome or Safari:
     https://10.247.60.51:5173/tracker
  3. Accept SSL certificate warning.
  4. Enter Full Name, select Semester, toggle "Bypass Time Restriction" (if testing off-hours).
  5. Tap "Share My Location" and grant browser GPS permissions.
  6. The live marker appears immediately on the Admin Map and within the 24h History Table.

11. SYSTEM LIMITATIONS & FUTURE RESEARCH ROADMAP
================================================================================
Known Limitations:
1. OS Background Throttling: Mobile operating systems (especially iOS Safari) throttle 
   JavaScript timers and pause WebSocket transmissions when the device screen locks.
2. Concrete Structural Attenuation: Multistory institutional buildings cause GNSS signal 
   attenuation, triggering occasional +/- 10m drift.
3. Process Memory Bound: Active tracking state is stored in Node.js process memory, 
   capping single-instance concurrency at approximately 80 to 100 concurrent streams.

Future Roadmap & Enhancements:
1. Polygonal Campus Geofencing:
   Implement Ray-Casting Point-in-Polygon (PIP) algorithms to automatically detect 
   when coordinates fall outside campus geographic boundaries and trigger alerts.
2. Offline-First Telemetry Buffer (IndexedDB):
   Cache breadcrumb coordinates locally when mobile connection drops and bulk-sync 
   upon network restoration.
3. Distributed Multi-Campus Scaling:
   Replace local RAM history store with a Redis Pub/Sub cluster to scale past 
   5,000+ simultaneous student connections.
