Q: Which parts did you personally develop?
A: I personally developed the entire Backend Architecture, Socket Gateway, and Data Persistence Engine:
   - Programmed `backend/server.js`: Initialized the Express application and Socket.IO server with CORS.
   - Built the institutional time gate function `isCollegeTime()`: Enforces the 9:00 AM – 4:15 PM IST window using the `Asia/Kolkata` timezone to prevent client device clock spoofing.
   - Implemented the 80-connection concurrency limiter (`Object.keys(activeStudents).length >= 80`) to safeguard server performance.

   - Built the entire storage engine in `backend/historyStore.js`:
     * Designed the composite key deduplication logic: `lowercase(name) + "___" + lowercase(semester)`.
     * Implemented in-place deduplication: Ensures each student occupies exactly 1 active record in memory and disk, eliminating database row bloat.
     * Engineered the disconnect coordinate freezing logic: Freezes the student's last-known coordinates upon disconnect and triggers the 24-hour countdown.
     * Built the automated sliding-window garbage collector: Runs every 15 minutes (`setInterval`) and prunes records older than 24 hours.
     * Implemented asynchronous disk persistence to `backend/data/location_history.json`.
   - Developed the REST API endpoints: `GET /api/history` (with search and semester query filters) and `GET /api/history/stats`.

3. DATABASE ARCHITECTURE
------------------------
Q: Your current system uses in-memory storage + JSON file persistence, correct?
A: Yes, correct. Active records reside in a fast JavaScript in-memory array (`historyCache`) and are asynchronously committed to a flat JSON file (`backend/data/location_history.json`).

Q: If they ask, “Why didn't you use MySQL/MongoDB?”, what is the answer?
A: 
   1. Sub-Millisecond Speed: GPS coordinates arrive continuously every 1–2 seconds. In-memory array operations execute in sub-milliseconds without connection pooling or query parsing delays.
   2. Ephemeral Data Lifecycle: Student coordinates in this system are transient and auto-expire after 24 hours. Heavyweight relational schemas with ACID transaction overhead are unnecessary for temporary telemetry.
   3. Zero Daemon Setup & Maximum Portability: It eliminates the requirement to install, configure, and maintain external database daemons (like `mongod` or `mysqld`), allowing the application to run anywhere instantly with zero configuration.
   4. Storage Efficiency: Because of our in-place deduplication composite key (`name___semester`), 80 students generate less than 150 KB of JSON data.


4. AUTHENTICATION MECHANISM
---------------------------
Q: Is the admin authentication currently just the hardcoded admin/admin123 login?
A: Yes. In `frontend/src/pages/AdminLogin.jsx`, credentials are verified against `id === 'admin'` and `password === 'admin123'`.

Q: Is there JWT/session authentication, or not?
A: It uses browser `sessionStorage`:
   - Upon successful login, `sessionStorage.setItem('adminAuth', 'true')` is stored.
   - Protected client-side routing is enforced in `App.jsx` using a `<ProtectedRoute>` component that redirects unauthorized users to `/admin-login`.
   - Backend API endpoints are currently open for demonstration purposes. Migrating to server-issued JWTs (JSON Web Tokens) stored in `httpOnly` secure cookies with bcrypt password hashing is noted as an enterprise production enhancement.


5. DEPLOYMENT SETUP
-------------------
Q: Are you presenting it as a local/demo system, or is it deployed online?
A: It is presented as a Local Demonstration System with Remote Cellular Access:
   - Host Laptop: Runs the Node.js backend (port 5000) and the Vite React frontend (port 5173).
   - Same Wi-Fi Network Access: Any mobile phone on the same Wi-Fi connects directly via `https://<Host-IP>:5173/tracker` (enabled by `@vitejs/plugin-basic-ssl`).
   - Remote 4G/5G Cellular Access: We use `npm run tunnel`, which executes an encrypted reverse SSH tunnel via `localhost.run` (`ssh -R 80:localhost:5173 localhost.run`), generating a public HTTPS link (e.g., `https://xxxx.lhr.life/tracker`) accessible over mobile data.
   - Why not deployed on cloud providers (e.g., Vercel / Render)?
     Free cloud hosting tiers frequently sleep or terminate persistent WebSocket connections, introduce 20–30 second cold-start delays, and restrict custom port tunneling. Running locally guarantees real-time sub-60ms performance.

Potential Demo Issues & Instant Solutions:
1. Browser SSL Certificate Warning ("Connection is not private"):
   - Explanation: Vite Basic SSL uses self-signed certificates for local HTTPS development.
   - Fix: Tap "Advanced" -> "Proceed to IP (unsafe)".
2. "Outside of college hours (9:00 AM to 4:15 PM IST)" Error:
   - Explanation: The institutional time-window rule is actively blocking out-of-hours tracking.
   - Fix: Check the "Bypass Time Restriction" checkbox on the mobile tracker screen.
3. Mobile Phone Can't Open URL:
   - Fix: Verify that the phone and laptop are on the same Wi-Fi network and the host IP is typed correctly, or switch to the `npm run tunnel` public link.
4. "Geolocation Permission Denied":
   - Fix: Go to phone browser site settings, reset location permissions to "Allow", and refresh.
